# 네이버 커머스 API 전환 분석/진행 내역 (2026-02-24)

## 0) 문서 목적

Analytics(웹 5188 / API 5189)의 “내 상품 추적/상품지수/리뷰 분석(예정)”에서 사용하던 **크롤링 기반 수집**을 줄이고,
가능한 영역을 **네이버 커머스 API 기반**으로 전환하기 위한 분석 결과와, 본 대화에서 실제로 수행된 작업(원복 포함)을 기록한다.

## 2) “내 상품 추적” 수집 항목을 API로 대체 가능한지(핵심 결론)

### 2.1 대체가 쉬운 영역: “내 스토어 상품 메타”

사용자가 확정한 조건:
- **경쟁사(타 스토어) 제외**
- **상품번호(productNo)는 URL 마지막 숫자와 동일**
  - 예: `https://smartstore.naver.com/<mall>/products/<productNo>`

이 조건이면, “내 상품 추적”에서 필요한 **상품 메타(상품명/가격/카테고리/대표이미지/판매상태/재고/전시상태 등)**는
크롤링 대신 커머스 API로 수집하는 방향이 유력하다.

### 2.2 대체가 어려운 영역: “쇼핑 검색 순위/경쟁상품/페이지 지표”

커머스 API 성격상 아래 항목은 **API만으로 완전 대체가 어렵다**.
- **쇼핑 검색 ‘순위’**: 검색 결과 랭킹(1~500 등) 스냅샷은 커머스 API 범위를 벗어날 가능성이 큼.
- **경쟁상품 상세**: 내 판매자 권한이 없는 타 판매자 상품은 커머스 API로 동일 수준 조회가 어려움.
- **상품 페이지 지표(리뷰수/평점/배지 등)**: 커머스 API가 동일 지표를 직접 제공하지 않는 항목이 존재할 수 있어, 일부는 유지/대체 전략 필요.

대안:
- 경쟁상품 “기본 메타” 정도는 네이버 쇼핑 검색 OpenAPI로 일부 보완 가능하지만, 검색 기반이라 매칭/정합성 로직이 필요하다.
  - 문서: [네이버 쇼핑 검색 API](https://developers.naver.com/docs/serviceapi/search/shopping/shopping.md)

## 3) 커머스 API의 “정확한” 인증/호스트 구조(공식 문서 기준)

### 3.1 인증 방식

커머스 API는 OAuth2 규약 중 **Client Credentials**를 사용한다.

- 문서: [인증](https://apicenter.commerce.naver.com/docs/auth)

핵심 포인트:
- 토큰 발급 시 **bcrypt 기반 전자서명(client_secret_sign)** 생성이 필요(클라이언트 시크릿을 직접 전달하지 않는 방식).
- `401` + 응답 코드 `GW.AUTHN`이면 토큰 만료 가능성이 높으므로 **토큰 재발급 후 재시도**를 권장한다.

### 3.2 운영 호스트(베이스 URL)

커머스 API 운영 호스트는 다음과 같이 문서에 명시되어 있다.

- 문서: [Restful API](https://apicenter.commerce.naver.com/docs/restful-api)
- 운영 호스트: `https://api.commerce.naver.com/external`

즉, “`/external`이 단지 논리적 구분일 뿐 실제 호출 경로가 아니다”라는 주장과는 **공식 문서 내용이 일치하지 않는다**.

## 4) 판매 지표(7일 판매수/예상판매수/예상매출/재구매 등) 전환 전략

### 4.1 문제

기존 크롤링으로 가져오던 아래 지표는 커머스 API가 “완성 지표”로 직접 제공하지 않을 수 있다.
- 7일 판매수
- 예상 판매수
- 예상 매출액
- 최근 3개월 재구매 등

### 4.2 구조적 해결: “원천 판매 데이터 수집 → 일 단위 적재 → 지표 산출”

커머스 API의 **주문 조회(상품 주문)**를 원천으로 수집하고,
DB에 “어제 데이터 추가 + 변경 반영” 방식으로 적재/재집계하면, 위 지표는 Analytics DB에서 안정적으로 산출 가능하다.

주문 조회 묶음은 “상품 주문 목록/상세/조건형/변경 내역 조회” 등을 제공한다.
- 문서: [주문 조회](https://apicenter.commerce.naver.com/docs/commerce-api/2.68.0/%EC%A3%BC%EB%AC%B8-%EC%A1%B0%ED%9A%8C)
- 스키마(상품 주문 상세 포함): [상품 주문 정보 구조체](https://apicenter.commerce.naver.com/docs/commerce-api/2.68.0/schemas/%EC%83%81%ED%92%88-%EC%A3%BC%EB%AC%B8-%EC%A0%95%EB%B3%B4-%EA%B5%AC%EC%A1%B0%EC%B2%B4)

권장 설계 포인트(운영 안정성):
- “어제만 append”로 끝내지 말고, **취소/반품/교환 등 사후 변경을 반영**하도록
  - 변경분 기반 증분 수집(변경일시 기준) + 영향 날짜 재집계
  - 또는 최근 N일(예: 14~30일) 구간 재집계를 병행

개인정보(재구매 계산 등) 관련:
- 주문자 식별자를 그대로 저장하지 말고, 서버 비밀키로 **HMAC/해시한 buyer_key**로 저장하는 방식 권장.

## 5) 리뷰 수집/AI 답변 자동화(검증 필요 사항)

대화 중 “리뷰 목록 조회/답글 등록” 엔드포인트 예시가 제시되었으나,
공개적으로 확인 가능한 문서/검색 결과만으로는 해당 엔드포인트가 **정확히 문서화되어 노출되는지**를 확정하지 못했다.

확실히 확인된 “콘텐츠 관리” 계열 예:
- 고객 문의(Q&A) 답변 등록/수정 카테고리 존재
  - 문서: [고객 문의 답변 등록/수정](https://apicenter.commerce.naver.com/docs/commerce-api/current/%EA%B3%A0%EA%B0%9D-%EB%AC%B8%EC%9D%98-%EB%8B%B5%EB%B3%B5-%EB%93%B1%EB%A1%9D-%EC%88%98%EC%A0%95)

따라서 리뷰 자동화는 다음 순서로 진행이 안전하다.
1) 커머스 API 센터(로그인 상태 포함)에서 **리뷰 API 문서(경로/파라미터/응답 스키마)**를 확정
2) 리뷰 원천 테이블 + AI 분석 테이블 + 발송(답변 등록) 감사/재시도 테이블로 분리 설계
3) 레이트리밋(429), 토큰 만료(401/GW.AUTHN) 재시도, 중복 발송 방지(Unique 제약)까지 포함

## 6) “API 세팅(UI)” 관련 실제 진행 내역(ERP2-dev에서 수행 → 원복)

대화 중 “메뉴 API 세팅에 커머스 API 정보를 입력 가능” 요청이 있었고,
Cursor 워크스페이스가 `C:\dev\ERP2-dev`로 열려 있어 ERP2-dev의 `설정 → API 키 관리` 화면(`ApiCredentialsView`)에
`NAVER_COMMERCE` 섹션을 일시적으로 추가했다가,

> “ERP2-dev(회계/판매 프로그램)에 영향이 있으면 원복” 요청에 따라

해당 변경은 **ERP2-dev에서 완전히 원복**되었다.

즉, 이 문서가 저장된 `ERP2-analytics`에는 아직 “커머스 API 입력 UI”가 추가된 상태가 아니며,
필요하다면 **ERP2-analytics 저장소에서** 별도로 동일 기능을 구현해야 한다.

## 7) 다음 구현 단계(ERP2-analytics에서 수행)

우선순위 권장:
1) **커머스 API 자격증명 저장소**(DB 또는 설정 스토어) 확정
2) **상품번호(productNo) 기반 상품 메타 수집** API/배치 구현(크롤링 제거 1단계)
3) **주문(상품 주문) 기반 일별 판매 집계** 배치 구현 → 7일 판매/예상/재구매 지표 산출
4) 리뷰 API는 문서/권한 확정 후 별도 트랙으로 진행

운영 원칙:
- 크롤링(CDP)은 “순위 수집 등 불가피한 영역”에만 최소한으로 남기고,
- 나머지는 커머스 API 기반으로 전환해 차단/유지보수 리스크를 줄인다.
