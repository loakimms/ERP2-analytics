# 키워드 순위 수집 시간 단축 분석

## 현재 구조

- **진입점**: `POST /search-rank/crawl/category` (단일 상품 + 해당 상품 수기 키워드 목록)
- **백엔드**: `_run_openapi_rank_job()` → 네이버 쇼핑 검색 OpenAPI(shop.json)로 순위 조회 후 `tracked_product_rank_daily`(source='openapi')에 저장
- **프론트**: 상품별로 순차 수집 — 한 상품 수집 완료 후 다음 상품 시작 (`runNextRankCollectInPlan`)

### 병목

1. **키워드 단위 순차 처리**  
   한 상품당 약 100개 키워드를 **한 개씩** 순차로 처리한다.  
   - 키워드마다 1~N회 OpenAPI 호출(페이징, 최대 rank 120/500 등)
   - 호출 간 0.05~0.12초 슬립(페이징 구간만 해당, 키워드 간 슬립 없음)
   - 결과: 상품당 100키워드 × (평균 1~2회 호출) ≈ 100~200회 순차 요청 → 상품당 수 분~십 수 분 소요 가능

2. **상품 단위 순차**  
   여러 상품을 수집할 때, 한 상품 job이 끝난 뒤에만 다음 상품 수집이 시작된다.

3. **네이버 API 제약**  
   - 일일 25,000회 호출 한도(클라이언트 ID 기준)  
   - QPS 제한은 문서에 명시되지 않음 → 과도한 동시 호출은 429 가능성 있으므로 적당한 동시도 유지 필요

## 개선 방향

### 1. 키워드 단위 병렬화 (구현 대상)

- **아이디어**: 한 상품 내 키워드만 동시에 여러 개 처리.  
  OpenAPI는 418/캡차 이슈가 거의 없으므로, 적당한 동시 요청으로 체감 시간을 크게 줄일 수 있음.
- **방식**: `ThreadPoolExecutor`로 키워드별 `_openapi_fetch_shop_items` 호출(및 페이징)을 병렬 실행.
- **동시도**: 환경 변수 `OPENAPI_RANK_CONCURRENCY` (기본 8, 권장 5~10).  
  일일 한도는 25,000회이므로 동시도 8이면 상품당 100키워드 시 이론상 약 1/8 수준으로 구간 단축.
- **DB**: 스레드에서는 API 호출·매칭만 수행하고, **저장은 메인 스레드에서만** 수행(세션 비공유, 기존 merge 로직 유지).
- **취소**: job 취소 시 이미 제출된 작업은 끝날 수 있으나, 메인 스레드에서 취소 플래그를 보고 더 이상 저장하지 않고 종료.

### 2. 페이징 슬립 (선택)

- 현재: 페이징 시에만 `time.sleep(0.05~0.12)` 적용.
- 병렬화 시 동시 요청 수가 제한되므로, 페이징 슬립은 유지하거나 약간 줄여도 됨(필요 시 나중에 튜닝).

### 3. 상품 단위 병렬화 (미적용)

- 한 번에 여러 상품을 동시에 수집하면 전체 완료 시간은 더 줄일 수 있음.
- 다만 프론트/백엔드가 job 1개 = 상품 1개 구조라서, 상품 병렬화는 API 설계·UI(진행 상태 표시 등) 변경이 필요.
- 1단계에서는 **키워드 병렬화만** 적용하고, 상품 단위는 기존처럼 순차 유지.

## 적용 결과 요약

- **변경 파일**: `api/main.py`
  - `_openapi_fetch_rank_for_one_keyword()` 추가: 키워드 1개에 대한 OpenAPI 호출·매칭만 수행(DB 미사용).
  - `_run_openapi_rank_job()`: `OPENAPI_RANK_CONCURRENCY` 읽어 1 초과 시 `ThreadPoolExecutor`로 키워드 병렬 처리, 결과는 메인 스레드에서 기존 로직으로 저장.
- **환경 변수**: `OPENAPI_RANK_CONCURRENCY` (기본 8, 1이면 기존 순차 동작).

이렇게 하면 제품당 약 100개 키워드 수집 시, 네이버 API를 쓰는 구간의 체감 시간을 줄일 수 있다.
