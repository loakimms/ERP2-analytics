1. 시스템 개요

프로그램 목적

네이버 검색광고, GFA, 스마트스토어, 쇼핑 검색/순위, 리뷰/Q&A, 판매 데이터를 모아 광고와 상품 운영 의사결정을 지원하는 Analytics 전용 시스템입니다.

2. 전체 아키텍처

브라우저 UI, FastAPI, DB, Host Agent, 외부 네이버/AI 서비스가 역할을 나누어 동작합니다.

1 사용자 UI React 화면에서 메뉴 선택, 기간/상품/키워드 조건 설정, 수집 실행, 분석 실행
2 FastAPI 권한 확인, 수집 job 생성, API 호출, DB 저장, 분석 응답 생성
3 PostgreSQL 일자별 fact, 원천 raw, 파생 분석, 사용자 설정, 실행 이력 보존
4 Host Agent/CDP 네이버 화면 기반 수집, 파일 다운로드, 로그인 세션 재사용, 부분 저장
5 AI Engine OpenAI/Gemini 기반 분석, 답글 초안, GFA 소재 생성/평가, 운영 판단 생성

로컬 실행 구조

  • analytics-master-web: React 빌드 결과를 nginx로 제공
  • analytics-master-api: FastAPI/uvicorn 서버
  • analytics-master-db: PostgreSQL 16-alpine
  • Host Agent: Windows PowerShell 프로세스, UI/CDP 자동화 담당

데이터 흐름 요약

  • 공식 API 가능 영역: SearchAd, Commerce, 일부 OpenAPI 기반 쇼핑 검색
  • 공식 API 한계 영역: GFA UI 보고서, 광고 노출 진단, 리뷰 엑셀, 구매 키워드 다운로드
  • CDP 수집 결과는 API의 collector endpoint로 제출되어 DB에 upsert됩니다.

Frontend 라우팅/인증

  • React entry는 web/src/main.tsx, root는 web/src/modules/App.tsx입니다.
  • BrowserRouter → AuthProvider → AuthGate → AppShell 순서로 UI가 구성됩니다.
  • 기본 route는 /analytics/rank/tracking이며, /, /analytics, unknown path도 내 상품 추적으로 redirect됩니다.
  • API base는 VITE_ANALYTICS_API_BASE_URL 또는 기본 http://localhost:5189입니다.

Backend 인증/권한

  • 운영/NAS에서는 Firebase ID Token 기반 Bearer 인증을 사용합니다.
  • 수집 Collector는 x-analytics-collector-token 또는 x-erp2-collector-token으로 Firebase 인증을 우회합니다.
  • 공개 allowlist는 health/version/docs/openapi 및 Host CDP discovery 일부 endpoint입니다.
  • DB migration framework는 별도 도구 없이 create_all과 init_db()의 방어적 ALTER TABLE IF NOT EXISTS를 사용합니다.

저장 정책 핵심

프로그램은 화면 진입 때마다 외부 서비스를 다시 긁는 방식을 줄이고, 수집 시점의 스냅샷을 DB에 보존한 뒤 메뉴는 저장 데이터를 재사용하는 방향으로 설계되어 있습니다. 실패 데이터가 성공 데이터를 덮어쓰지 않도록 일부 upsert에는 성공값 보호 로직이 들어 있습니다.

5. 데이터 수집 프로세스

중앙 수집 허브는 COLLECTION_TASK_REGISTRY와 /collection/* API로 작업을 관리합니다.

1작업 선택데이터 수집 메뉴에서 수집 task를 선택하거나 schedule/run-all 실행
2Job 생성API가 collection_job_run에 실행 이력 생성
3실행 위치 결정server_api/server_batch는 API가 직접, host_cdp는 Host Agent가 claim
4수집/다운로드API 호출 또는 Chrome CDP 조작, 필요 시 파일 다운로드
5저장 검증target table row 수와 coverage를 확인해 SUCCESS/PARTIAL/FAILED 결정

Host Agent/CDP 동작

Host Agent 역할

  • Windows 로컬/NAS Collector PC에서 tools/host-agent.ps1 실행
  • 로컬 HTTP 서버 http://127.0.0.1:9230 제공
  • Chrome CDP 포트 9223으로 브라우저 조작
  • 로그인 세션을 재사용해 네이버 화면에서 보고서 요청/다운로드
  • 작업별 stage/event를 API에 제출해 진행 상황 표시

대표 CDP 모드

  • page_metrics: 상품 상세 메트릭
  • purchase_keywords_cdp: 구매 키워드 엑셀
  • gfa_performance_report_cdp: GFA 성과보고서
  • gfa_campaign_inventory_cdp: GFA 캠페인 목록
  • gfa_adgroup_inventory_cdp: GFA 광고그룹 목록
  • gfa_creative_detail_cdp: GFA 소재 상세
  • reviews_excel_cdp: 리뷰 엑셀
  • ad_rank_diagnosis_cdp: 광고 노출 진단
광고 상품 순위(CDP) 특화 프로세스

광고 노출 진단은 공식 API로 키워드×성별×연령×지면별 실시간 순위를 제공하지 않기 때문에, 광고센터의 exposure-status 화면을 CDP로 조작합니다. 현재 순위 범위는 92위까지이며, 키워드는 내 상품 추적의 그룹1 핵심 키워드를 사용합니다. 결과는 상품별로 저장되고, 성공/미노출/실패와 함께 검색광고/ADVoost 구분도 저장할 수 있습니다.

1상품/키워드 plan 생성API가 active 광고 상품, 그룹1 키워드, core preset 조건을 묶음
2광고센터 진입Host Agent가 노출현황보기 화면으로 이동
3조건 선택키워드 고정 → 성별/연령 → 지면 순서로 조회
4결과 확인결과 테이블 안정화 후 92위까지 row text를 분석
5부분 저장조건 하나가 끝날 때마다 partial-results로 DB 저장

7. 로컬/NAS 운영

운영 안정성의 핵심은 불변 태그, lock 파일, candidate 검증 후 승격입니다.

표준 재빌드 흐름

1Build Candidate새 tag analytics_YYYYMMDD_HHMMSS 생성
2Switch & Verifycandidate lock으로 web/api 기동, version 증거 확인
3Promote검증 PASS면 master lock으로 승격

scripts/analytics_rebuild_and_verify.ps1 한 번으로 수행됩니다.

증거 3종 세트

  • 컨테이너 image tag가 lock의 ANALYTICS_IMAGE_TAG와 일치
  • Web http://localhost:5188/version.json의 imageTag 확인
  • API http://localhost:5189/api/version의 imageTag 확인
운영 명령/스크립트 용도 주의사항
scripts/cmd-analytics-local.ps1로컬 stack 기동Web 5188, API 5189

금지/주의 흐름

lock 없이 직접 docker compose up을 실행하거나, latest 같은 가변 tag를 쓰거나, 실행 중 컨테이너에 dist/를 덮어쓰는 배포는 롤백/착시 문제를 만들 수 있으므로 사용하지 않습니다.

운영 Safeguard

잘못된 폴더 실행 방지

CANONICAL_ROOT.txt와 스크립트 root check로 다른 프로젝트 오염을 막습니다.

legacy compose 차단

root docker-compose.yml는 legacy profile로 묶여 기본 실행을 피하도록 설계되어 있습니다.

NAS CDP fail-fast

NAS compose는 REQUIRE_HOST_CDP=1로 내부 Chromium fallback 없이 실패를 드러냅니다.

Host Agent 버전 Drift 방지

UI 요구 버전, Agent 스크립트, installer bundle 버전을 검증합니다.

Stale Job 정리

API startup과 매일 scheduler reset에서 중단된 수집 job을 DB persistence 기준으로 reconcile합니다.

NAS 배포 중 502 완화

NAS 배포는 web stop → api warmup → web start 순서로 진행합니다.
