# 키워드 순위 수집: TOP 깊이 / 동일 키워드 일괄 / 병렬화 분석

## 1. TOP500 vs TOP1000 — “500으로 설정했는데 왜 1000으로 고정되나?”

### 코드상 동작

| 위치 | 내용 |
|------|------|
| **프론트** | `rankCrawlDepth` 초기값 `500`, 셀렉트로 40/80/120/500/1000 선택 가능. 요청 시 `limit: TOP_LIMIT` (= `rankCrawlDepth \|\| RANK_CRAWL_TOP_LIMIT`) 전달. |
| **API 스키마** | `CategoryCrawlRequest.limit` 기본값 **500**, `ge=10`, `le=1000`. |
| **API 핸들러** | `limit = int(getattr(payload, "limit", 120) or 120)`, `limit = max(10, min(1000, limit))` → **payload의 limit 그대로 사용**(500이면 500). |
| **백그라운드 job** | `max_rank = max(10, min(1000, int(limit or 120)))` → **limit 값이 곧 검색 깊이(TOP N)**. |
| **OpenAPI 페이징** | `while remaining > 0 and start <= 1000` → **1000은 네이버 API 상한(start≤1000)**이지, “항상 1000까지 수집”이 아님. `remaining = max_rank`에서 시작하므로 limit=500이면 500건만 요청 후 종료. |

**결론 (코드 기준)**  
- 사용자가 TOP500을 선택하면 `limit: 500`이 전달되고, API도 `max_rank=500`으로 **500위까지만** 수집한다.  
- **“항상 1000으로 고정”**되도록 하는 하드코딩은 없다. 1000은 스키마 상한·OpenAPI 상한일 뿐.

### 실제로 1000으로 동작한다면 확인할 것

1. **요청 body**: 개발자 도구 Network 탭에서 `POST .../search-rank/crawl/category` 요청의 payload에 `limit: 500`이 들어가는지 확인.  
2. **UI 상태**: 수집 모달에서 “깊이” 셀렉트가 TOP500이 아닌 TOP1000으로 보이지 않는지 확인.  
3. **API 로그**: 수집 시작 시점에 `[openapi-rank-job] start ...` 로그에 사용된 `limit`(또는 그에 대응하는 `max_rank`) 값을 한 번 로그로 남기면, 실제로 500이 들어오는지 확인 가능.

## 2. 같은 키워드를 여러 상품에서 한 번에 처리할 수 있는지

### 현재 방식

- **요청 단위**: 상품 1개(`product_url`) + 그 상품의 키워드 목록.  
- **OpenAPI 호출**: 키워드 1개당 1회 검색(shop.json) → 해당 키워드의 검색 결과 리스트 수신 → 그 안에서 **해당 상품 1개의 순위**만 매칭해 저장.

따라서 상품 A·B·C가 **같은 키워드 K**를 쓰면:

- 지금: A 수집 시 K 1회, B 수집 시 K 1회, C 수집 시 K 1회 → **K에 대해 OpenAPI 3회** 호출.

### “한 번의 수집으로 같은 키워드 일꼐 처리” 가능 여부

**가능하다.**  
동일 키워드 K에 대해 OpenAPI는 **1번만** 호출하고, 검색 결과 리스트에서 **K를 쓰는 모든 상품**의 순위를 한 번에 매칭해 저장하면 된다.

- **입력**: 여러 `product_url` + 상품별 키워드 목록(또는 product → keywords 맵).  
- **중간 단계**: 키워드 K에 대해 “K를 등록한 상품 URL 목록”을 만든다.  
- **수집**:  
  - 유니크 키워드마다 OpenAPI 1회 호출.  
  - 응답 리스트에서 각 상품 URL(또는 product_id/catalog_id)을 매칭해 순위를 구하고,  
  - `(date, product_url, keyword, rank)` 를 상품별로 저장.

**효과**  
- 상품 10개, 공통 키워드 50개 + 상품별 고유 키워드 30개 정도라면:  
  - 현재: 10 × (50+30) = 800회 OpenAPI.  
  - 키워드 기준 일괄: 유니크 키워드 수만큼만 호출(예: 50 + 10×30 = 350회, 실제로는 유니크 수에 따라 더 줄어듦).  
→ **동일 키워드가 많을수록 호출 횟수·수집 시간 단축 가능.**

구현 시 고려할 점:

- API: “여러 상품 + 상품별 키워드”를 받는 배치 엔드포인트(또는 기존 엔드포인트 확장).  
- 한 번에 너무 많은 상품/키워드를 넣지 않도록 상한(예: 상품 수, 키워드 수) 두기.  
- job 상태·진행률을 “상품 단위”가 아니라 “키워드(또는 태스크) 단위”로 정의해 UI/폴링과 맞추기.

## 3. 수집 방식: 상품별 순차 vs 과거 “여러 상품 동시” — 수집 시간

### 현재 구조

- **상품**: 한 번에 **1개 상품**만 처리.  
  - 프론트: `startRankCollectAllMissingProducts` → `rankCollectPlanRef`에 (날짜, URL 목록) 저장 후 `runNextRankCollectInPlan()`으로 **한 상품씩** `startRankCollectNowForProduct(targetUrl, targetDate)` 호출.  
  - 한 상품 수집이 SUCCESS로 끝나면 그다음 상품으로 이어서 진행.
- **키워드**:  
  - `OPENAPI_RANK_CONCURRENCY=1`(기본): 해당 상품의 키워드를 **순차** 처리.  
  - `OPENAPI_RANK_CONCURRENCY>1`: 해당 상품 내에서만 **키워드 단위 병렬** (ThreadPoolExecutor).

즉, **“여러 상품을 동시에”** 돌리는 구조는 없다.  
상품은 완전히 순차(1번 → 2번 → 3번 …), 그 안에서만 키워드가 순차 또는 병렬이다.

### 과거와 비교했을 때

- **이전**: (설명만으로 추정) 여러 상품을 동시에 수집했을 가능성(예: 여러 job 동시 실행, 또는 한 job에 여러 상품).  
- **지금**:  
  - 상품 N개면 **N번의 job**이 **차례로** 실행됨.  
  - 수집 시간 ≈ (상품1 키워드 수 + 상품2 키워드 수 + … ) × (키워드당 평균 시간) / `OPENAPI_RANK_CONCURRENCY` (상품 내 병렬만 해당).

그래서 **“수집 시간 단축” 측면에서 현재는 상품 단위 병렬이 빠져 있다**는 말이 맞다.

### 단축 방향 정리

1. **상품 단위 병렬**  
   - 여러 상품에 대해 **동시에** job을 띄우기(프론트에서 동시에 여러 번 `POST /crawl/category` 호출하고, 각각 job_id로 폴링).  
   - 주의: 동시 job·OpenAPI 호출이 많아지면 레이트 리밋·부하 가능성 있으므로 상한(동시 job 수, 예: 2~3개) 두는 것이 안전.

2. **키워드 기준 일괄 (위 2번)**  
   - 같은 키워드를 여러 상품에서 한 번에 처리해 OpenAPI 호출 횟수를 줄이기.

3. **현재 옵션 활용**  
   - `OPENAPI_RANK_CONCURRENCY`를 1보다 크게(예: 4~8) 주어, **한 상품 안**에서만이라도 키워드 병렬로 처리.

## 요약 표

| 항목 | 현재 동작 | 비고 |
|------|-----------|------|
| TOP 깊이 | UI에서 500 선택 시 `limit: 500` 전달, API도 500위까지 수집. 1000은 스키마/OpenAPI 상한만 해당. | 실제로 1000으로 보이면 요청 body·UI 선택값·API 로그로 limit 확인 필요. |
| 동일 키워드 | 상품별로 같은 키워드도 매번 OpenAPI 호출. | 키워드 기준 배치로 한 번에 처리 가능하며, 호출 수·시간 단축 가능. |
| 상품 병렬 | 상품은 1개씩 순차 수집. 키워드만 (옵션으로) 병렬. | 과거처럼 “여러 상품 동시”는 없음. 수집 시간 단축을 위해 상품 병렬·키워드 일괄 처리 검토 여지 있음. |
