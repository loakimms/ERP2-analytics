1. 문서 목적과 범위

1.1 목적

  • 현재 ERP2 Analytics의 실제 기술 구조, 메뉴, 데이터 자산, 수집 안정성, AI 운영센터 구조를 하나의 기준 문서로 통합한다.
  • 새로 추가되는 '종합상황실(Executive Command Center)'과 '분야별 Sub 상황실'을 기존 분석 메뉴 위에 얹는 운영 계층으로 설계한다.
  • 모니터링과 이상 대응만이 아니라 Optimize·Discover·Generate·Execute·Validate·Learn까지 포함한 전체 제품 목표를 고정한다.
  • 향후 Cursor 구현 시 임의 기준을 만들지 않도록 데이터 Source, 판단 책임, UI 책임, 실행 책임, 보류 조건을 구분한다.

1.2 이번 문서에서 다루는 범위

  • 현재 구현: React/Vite Web, FastAPI API, PostgreSQL, Windows Host Agent/CDP, Naver API, AI 분석·생성 기능.
  • 현재 메뉴: AI 운영센터, 키워드 분석, SA, GFA, 검색·쇼핑 순위, 판매, 리뷰/Q&A, SEO, 설정.
  • 추가 설계: 종합상황실, Sub 상황실, 공통 상태/기회 계약, Case/Decision/Work Order/Outcome, Content Factory, Outcome Learning.
  • 향후 확장: 신규 마케팅 도메인이 추가되어도 종합상황실을 대규모 수정하지 않는 공통 Contract 구조.

2. 프로젝트 최종 정의

2.1 제품 한 문장

  • ERP2 Analytics는 단순 모니터링 대시보드가 아니라, 광고·오가닉·판매·구매키워드·GFA 소재·고객 VOC·Q&A·상품지수 등 이미 축적된 데이터를 통합하여 현재 상태를 감시(Monitor)하고, 기존 운영을 최적화(Optimize)하며, 새로운 성장 기회를 발굴(Discover)하고, 사람 승인 기반으로 실행(Execute)한 뒤 성과를 검증(Validate)하고 다음 판단에 학습(Learn)하는 마케팅 운영 의사결정 플랫폼을 목표로 한다.

2.2 제품이 답해야 하는 6개 질문

  • 지금 회사의 매출·광고·오가닉·상품·고객 상태는 정상인가?
  • 문제가 있다면 어느 플랫폼·SKU·키워드·캠페인·소재·고객 구간에서 시작되었는가?
  • 현재 집행 중인 마케팅에서 무엇을 올리고, 내리고, 유지하고, 중단해야 하는가?
  • 현재 집행하지 않는 새로운 광고 키워드·오가닉 성장 키워드·타겟·소재·콘텐츠 기회는 무엇인가?
  • 운영자가 승인한 조치를 누가·어디에·무엇을·얼마나 변경해야 하는가?
  • 실행 후 3/7/14/30일 결과가 실제로 좋아졌는가, 다음 정책에는 무엇을 학습해야 하는가?

2.3 핵심 운영 Cycle

  • Collect → Analyze → Monitor → Optimize → Discover → Decide → Generate → Execute → Validate → Learn.
  • 기존 완성 아키텍처의 Collect→Analyze→Judge→Decide→Generate→Publish→Monitor→Learn 구조와 충돌하지 않는다. Monitor/Optimize/Discover는 Judge를 운영 목적별로 세분화한 상위 제품 관점이다.

3. 현재 시스템 Fact Baseline

3.1 런타임/기술 Stack

  • Web: React 18 + Vite + TypeScript SPA. 로컬 5188, NAS 6188.
  • API: FastAPI + SQLAlchemy. 로컬 5189, NAS 6189.
  • DB: PostgreSQL. 로컬 host 5442, NAS 6442.
  • Host Agent: Windows PowerShell + Chrome CDP. NAS 운영 문서 기준 CDP 9223.
  • 배포: Docker immutable tag + version/lock 검증.

3.2 현재 데이터 자산 규모

  • 광고 검색어 약 49만 row, GFA 성과 약 20만 row, 쇼핑 검색 순위 약 15만 row, 내 상품 추적 순위 약 13만 row.
  • 광고 소재 약 12만 row, 광고 키워드 약 8만 row, 광고 노출 진단 약 1.8만 row, 구매 키워드 약 1.76만 row.
  • 리뷰 원문과 Q&A 원문이 상품/고객 Needs 및 전환장벽 판단의 근거 데이터로 축적되어 있다.

3.3 데이터 운영 특성

  • 공식 API 가능한 영역과 CDP/UI 다운로드가 필요한 영역이 공존한다.
  • 수집 시점 스냅샷을 DB에 저장하고 화면이 저장 데이터를 재사용하는 방향이 이미 확정되어 있다.
  • CDP 로그인/다운로드 의존 영역은 실패·부분 성공이 발생하므로 상황실은 '데이터 정상'과 '데이터 미수집'을 구분해야 한다.

4. 현재 메뉴/분석 자산과 역할 재정의

4.1 현재 메뉴 그룹

  • AI 운영 센터: 오늘의 실행, 상품별 운영 판단, 광고 운영 판단, 판매·전환 판단, 리뷰·VOC 판단, Q&A 전환장벽 판단, 수요·트렌드 판단, SKU 정책 센터, 실행 큐, 검증/설명 로그
  • 키워드(광고/오가닉) 분석: 광고 검색어 분석, 구매 키워드 분석
  • SA 광고분석: 캠페인 분석, 광고 그룹 분석, 소재 분석
  • GFA 광고분석: 운영 체크, 원본 분석, 소재 분석, 전략 도출, 소재 생성
  • 검색·쇼핑 순위 분석: 키워드 인사이트, 내 상품 추적, 내 광고 상품 추적
  • 판매 분석: 상품별 판매 현황, 상품 판매 상세
  • 리뷰 Q&A: 리뷰 관리, 리뷰 분석, Q&A 관리, Q&A 분석
  • SEO 분석: 상품명 SEO, 해시태그 SEO, 상품지수분석
  • 설정: 카테고리 사전, SEO규칙등록, API 세팅, AI 세팅, 데이터 수집, 메뉴동기화, 버전관리, 사용자관리

4.2 유지 원칙

  • 기존 상세 분석 메뉴는 폐기하지 않는다. 이들은 종합상황실/Sub 상황실의 Evidence Source다.
  • 종합상황실이 원천 데이터를 직접 다시 계산하지 않는다. 기존 분석 결과와 새 Decision Mart를 소비한다.
  • 분야별 상황실이 기존 상세 분석 메뉴를 대체하지 않고, '상태·위험·개선·기회·실행'을 압축해 연결한다.

4.3 현재 AI 운영센터의 한계

  • 점수·정책 라벨·권장 액션 문장과 큐 버튼만으로는 운영자가 '오늘 무엇을 해야 하는지' 즉시 판단하기 어렵다.
  • 승인 후 실제 작업지시와 Outcome이 약하면 실행과 학습이 끊긴다.
  • 따라서 상황실은 단순 KPI 카드가 아니라 Case → 선택 → Work Order → Outcome 흐름을 전면에 둬야 한다.

5. 사용자의 실제 매출 이상 분석 프로세스

5.1 하락 발생 시 10단계 원인 추적

  • 1) 매출 하락 여부와 기준기간 대비 변화 확인.
  • 2) 전체 시장 변화인지 특정 플랫폼(네이버/쿠팡 등) 변화인지 구분.
  • 3) 하락 플랫폼에서 오가닉 매출과 광고 매출 변화 비교.
  • 4) 메인 키워드 약 5개의 최근 검색량 및 3년 시즌성 확인.
  • 5) 오가닉 순위 변화와 신규/기존 고객 변화 확인.
  • 6) 광고 검색어와 구매 키워드 분석.
  • 7) SKU별 매출 변화와 SKU별 키워드 변화 확인.
  • 8) 오가닉 순위 변동 시 상품지수(클릭·매출·리뷰·최신성·패널티 등) 원인 확인.
  • 9) 최근 리뷰와 Q&A/VOC 분석.
  • 10) SA/GFA에서 캠페인→그룹→키워드/소재의 노출·클릭·CTR·구매·장바구니·전환매출·ROAS 변화를 추적.

5.2 정상/상승 시 운영

  • 이슈가 없으면 A-1~E-14 상태만 간단히 브리핑하고 상세 분석은 펼치지 않는다.
  • 상승 시에도 전체를 과잉 분석하지 않고, 상승 기여 요인과 지속 가능성·확대 여부만 요약한다.
  • 즉 상황실에는 Normal Mode와 Issue/Opportunity Mode가 함께 필요하다.

6. 종합상황실(Executive Command Center) 설계

6.1 역할

  • 회사 전체 마케팅 상태를 1분 이내에 파악하는 최상위 관제·성장 상황실.
  • 모든 세부 지표를 한 화면에 넣지 않고, 각 Sub 상황실의 상태·위험·개선·기회·검증 결과를 요약한다.
  • 운영자는 여기에서 '어디로 내려갈지' 결정하고, 상세 근거는 Sub 상황실/기존 분석 메뉴에서 확인한다.

6.2 종합상황실 4대 Queue

  • 위험(Risk): 즉시 대응해야 하는 매출 급락, 핵심 순위 급락, 광고비 급증, 품절/결제/수집 장애.
  • 개선(Optimize): CPC 조정, 예산 이동, 캠페인 순위 조절, SEO/상품 개선, 타겟/지면 최적화.
  • 기회(Discover/Grow): 신규 광고 키워드, 신규 오가닉 성장 키워드, 신규 타겟/소재/캠페인, SNS 콘텐츠 기회.
  • 검증(Validate): 최근 실행한 작업의 D+3/D+7/D+14/D+30 결과와 유지/롤백 판단.

6.3 상단 Executive Summary

  • 전체 매출, 주문, 결제율/전환율, 광고비, 광고매출, 오가닉매출, 신규/기존 고객, 환불/취소.
  • 플랫폼 상태: 네이버/쿠팡/기타 마켓.
  • 현재 이슈 수, 개선 후보 수, 신규 기회 수, 검증 대기 수, 데이터 신뢰도.
  • 위험은 빨간 점멸을 제한적으로 사용하고, 안정/상승은 녹색, 주의는 노랑, 집중 관리 주황, 데이터 부족 회색.

6.4 Drill-down

  • 전사 → 플랫폼/분야 → SKU → 키워드/캠페인/소재 → 원천 Evidence.
  • 종합상황실에는 긴 설명문 대신 상태, 핵심 숫자, Top N 원인, 현재 Action, 상세 이동 링크만 표시.

7. 분야별 Sub 상황실 공통 Contract

7.1 공통 4축

  • 현황(Current): 지금 성과와 주요 추세.
  • 위험(Risk): 악화·이탈·비효율·데이터 장애.
  • 개선(Optimize): 현재 운영 중인 캠페인/키워드/SKU를 어떻게 조정할지.
  • 기회(Discover): 현재 하지 않는 신규 키워드·타겟·소재·콘텐츠·SEO 기회.

7.2 공통 화면 구조

  • 상단 Snapshot: 핵심 상태 + 오늘의 Action + 데이터 신뢰도.
  • Risk/Opportunity Top N: 우선순위가 높은 Case만.
  • Optimization Matrix: 유지/증액/축소/중단/테스트/집중관리.
  • Evidence: 기존 상세 분석 메뉴로 Drill-down.
  • Operator Decision: 승인/보류/반려/수정후 실행.
  • Execution/Outcome: Work Order 상태와 사후 KPI.

7.3 공통 상태 Contract

  • STABLE, WATCH, RISK, OPPORTUNITY, DATA_GAP 같은 상태는 '시각 상태'이며 실행 명령과 분리한다.
  • Action은 KEEP, INVESTIGATE, SCALE, REDUCE, STOP, TEST, DEFEND, DISCOVER, HOLD 등 업무별 enum으로 별도 관리한다.
  • 데이터 부족은 정상으로 간주하지 않고 DATA_GAP/NOT_AVAILABLE로 표시한다.

8. Keyword Intelligence Sub 상황실

8.1 핵심 통합 데이터

  • 현재 광고 집행 키워드.
  • 매일 추적하는 오가닉 순위 키워드.
  • 실제 구매를 만든 구매 키워드/검색어.
  • 월 검색량·검색 트렌드·시즌성.
  • SKU별 매출/전환과 상품 관련성.

8.2 3개 키워드 Universe 결합 목적

  • 신규 광고 키워드 발굴.
  • 신규 오가닉 상위 진입 키워드 발굴.
  • CPC를 올려 광고 노출 순위를 높여야 할 키워드.
  • CPC를 내려도 되는 과투입 키워드.
  • 오가닉이 강해 광고 잠식 가능성이 있는 키워드.
  • 구매는 발생하지만 광고/오가닉 관리 목록에 없는 신규 수요 키워드.

8.3 A-1 운영 규칙

  • 기준 지면은 모바일 통합검색.
  • 1~3위: 매우 안정, 4~6위: 안정/1페이지 핵심, 7~10위: 위험, 11위 이하 또는 7~10위 키워드가 충분치 않으면 성장 필요.
  • 3일 연속 하락은 심각 신호.
  • 순위 밖 키워드가 10~15위로 진입하면 광고/SEO 성장 후보로 검토.
  • 오가닉 하락 → 유효 클릭 감소 → 매출 감소 → 상품점수 약화 → 추가 하락의 악순환을 방어하는 광고 전략 필요.

8.4 키워드 Opportunity Matrix 예

  • 광고 미집행 + 오가닉 10~15위 + 구매 기여 높음 → 신규 광고 + SEO 집중 후보.
  • 광고 집행 + 오가닉 1~3위 + 구매 낮음 → 광고 잠식/과투입 검토.
  • 광고 순위 낮음 + CVR/ROAS 높음 + 구매 중요 → CPC/입찰 상승 후보.
  • 광고 순위 매우 높음 + CPC 높음 + 오가닉 강함 → 입찰 하향 테스트.
  • 구매 키워드 존재 + 광고/오가닉 미관리 → 신규 키워드 등록 후보.

9. SA 광고 Sub 상황실

9.1 목적

  • 캠페인/광고그룹/키워드의 단순 성과 조회를 넘어서 '무엇의 순위를 올리고, 내리고, 유지하고, 끌지'를 도출한다.

9.2 입력

  • 캠페인·그룹·키워드별 노출, 클릭, CTR, CPC, 비용, 전환, CVR, 전환매출, ROAS, 평균 광고 순위.
  • 오가닉 순위, 구매 키워드 기여도, 검색량/시즌성, SKU 매출, 상품지수.
  • 지면별 성과(통합검색/쇼핑/개인화 등)와 광고-오가닉 잠식 여부.

9.3 출력

  • 입찰 상승/하락 후보와 목표 순위 구간.
  • 예산 증액/감액/중단 후보.
  • 광고 키워드 신규 추가/제외 후보.
  • 광고-오가닉 카니발 방어/축소 판단.
  • 캠페인/그룹별 집중·축소 우선순위.

9.4 A-5 지면 전략

  • 지면 × 키워드 × SKU 단위로 광고 강화/유지/축소/중단/오가닉 보호/테스트/데이터 부족을 분리.
  • 오가닉이 강한 지면에서는 광고 증분효과를 검증하고, 오가닉 위험 지면에서는 방어 광고를 검토.

10. GFA 광고 Sub 상황실

10.1 분석 차원

  • 캠페인 × 광고그룹 × 소재 × 타겟팅(잠재고객) × 성별 × 연령 × 노출 지면 × 시간 × SKU.
  • CTR/CVR/CPA/ROAS/전환매출 뿐 아니라 소재 특성(장면, 모델, 헤어상태, 감정, 구도, 색감, 소구포인트)과 연결.

10.2 최적화

  • 고성과 타겟·지면·소재 조합 확대.
  • 비효율 타겟/지면 축소 또는 제외.
  • 소재 피로·CTR 하락 탐지 후 교체 시점 제안.
  • 예산을 고성과 조합으로 재배분.

10.3 신규 생성

  • 고성과 소재의 공통 특성에서 신규 Creative Brief 자동 생성.
  • 타겟, 지면, 성별/연령, 메시지 각도, 카피 길이, 제품 노출, CTA, 이미지 프롬프트를 구조화.
  • 기존 GFA 생성기와 Action Queue를 연결해 분석→신규 소재 생성→검수→실행 후보까지 닫는다.

11. SKU·상품 Sub 상황실

11.1 SKU-first 원칙

  • 최상위 의사결정 단위는 SKU이며 키워드·캠페인·소재는 SKU 성과 개선을 위한 하위 액션이다.
  • 매출, 광고비, 오가닉 순위, 리뷰, Q&A, 상품지수, 가격/배송/재고, 신규/기존 고객을 SKU 단위로 결합한다.

11.2 주요 판단

  • 매출 급락/상승 SKU.
  • 광고 과투입 SKU.
  • 오가닉 방어가 필요한 SKU.
  • 리뷰/VOC 개선 후 광고 확대해야 하는 SKU.
  • 재고/품절 때문에 광고 확대하면 안 되는 SKU.
  • 성장 키워드와 신규 콘텐츠 기회를 가진 SKU.

12. 고객·VOC·Q&A Sub 상황실

12.1 역할

  • 리뷰/VOC에서 제품 문제와 고객 Needs를 도출하고, Q&A에서 구매 직전 전환장벽을 찾는다.
  • VOC가 해결되지 않은 SKU는 광고 확대를 보류할 수 있는 근거로 사용한다.
  • 반복 Q&A는 FAQ/상세페이지 수정/콘텐츠 주제로 전환한다.

12.2 생성 연결

  • 리뷰 답글 초안, Q&A 답변 초안, FAQ 초안, 상세페이지 개선 문구, 소재/콘텐츠 소구 포인트로 연결한다.

13. 수요·트렌드·성장 Sub 상황실

13.1 데이터

  • 메인 키워드 최근 검색량, 3년 시즌성, 구매 키워드 증가/감소, 오가닉 신규 진입, 플랫폼/시장 매출 변화.

13.2 목적

  • 시장 전체 변화와 자사 운영 문제를 구분.
  • 시즌 전 선제 광고/콘텐츠 준비.
  • 신규 수요 키워드와 SKU 연결.
  • 성장 신호를 GFA/SA/SEO/SNS 신규 캠페인으로 연결.

14. Case 중심 AI 운영 체계

14.1 Case 공통 구조

  • 제목: 대상 + 사건.
  • 상황 브리핑: 무엇이 변했는지, 비교 기준, 왜 중요한지.
  • 근거 숫자: 의사결정에 필요한 3~6개 지표.
  • 선택: 2~3개 실행 대안.
  • 작업지시 미리보기: 대상 ID, 변경량, 담당, 검증일.
  • 결정 후: Work Order ID, 상태, D+N 결과.

14.2 현재 정의된 7 Case

  • Case A — 돈 새는 광고 (키워드/예산)
  • Case B — 광고비 vs 실제 매출 (과투입)
  • Case C — 광고 전에 고쳐야 할 VOC
  • Case D — 구매 직전 막힘 (Q&A → FAQ)
  • Case E — 순위 급락 / 방어
  • Case F — 소재·카피 교체 (GFA/SA)
  • Case G — SNS/콘텐츠 패키지 (신규)

14.3 학습의 실제 단위

  • Case → Decision → Work Order → Outcome → Learning을 하나의 lineage로 보존.
  • action_queue 승인만으로는 학습이 아니다. 실제 변경량과 Outcome이 연결되어야 다음 추천 신뢰도를 갱신할 수 있다.

15. 신규 데이터 계약과 Decision Mart

15.1 유지할 Fact Layer

  • SA, GFA, Rank, Sales, Purchase Keywords, Reviews, Q&A, SEO, Product Index 등 기존 Fact/2차 가공 테이블은 Source of Truth로 유지.

15.2 신규/강화 Mart

  • decision_product_health_daily: SKU 단위 통합 건강도.
  • ai_decision_log: 근거, 기간, 룰 트리거, 신뢰도, 사용자 오버라이드.
  • action_queue: 실행 후보와 승인/반려.
  • action_outcome_daily: D+3/7/14/30 성과 delta.
  • content_artifact / sns_package: 생성 자산 버전, 채널, 상태.
  • feedback_knowledge: 승인/반려/성과 기반 재사용 지식.

15.3 종합상황실 공통 Domain Status Contract 제안

  • domain_id / status / primary_metric / change_rate / top_issue / risk_count / optimize_count / opportunity_count / action / confidence / data_freshness / evidence_links.
  • 각 Sub 상황실이 이 Contract를 출력하고 종합상황실은 이 Contract만 소비하도록 한다.
  • 새로운 분석 도메인이 2개 이상 추가되어도 종합상황실의 코어 로직 변경을 최소화한다.

16. API/서비스 구현 계획

16.1 기존 API 재사용

  • /ads/*, /gfa/*, /purchase/*, /sales/*, /search-rank/*, /ad-rank/*, /reviews/*, /qna/*, /ai/*.
  • 기존 API는 Evidence 및 원천 분석 제공자로 유지.

16.2 신규 API 제안

  • GET /command-center/summary : 전사 상태/위험/개선/기회/검증 Queue.
  • GET /command-center/domains : 각 Sub 상황실 공통 Status Contract.
  • GET /command-center/cases : 우선순위 Case 목록.
  • GET /sub-centers/{domain}/summary : 분야별 Snapshot.
  • GET /sub-centers/{domain}/opportunities : 신규 기회.
  • POST /decisions/{case_id} : 운영자 승인/보류/반려.
  • POST /work-orders : 구체 작업지시 생성.
  • GET /outcomes/{work_order_id} : 사후 성과 추적.

16.3 서비스 분리

  • AI Ops 로직을 단일 main.py에 몰지 않고 domain service + decision service + opportunity service + orchestration service로 분리.
  • 원천 데이터 계산, 룰 판정, GPT 해석, 작업지시 생성, 결과 검증의 책임을 분리.

17. AI Decision Engine 설계

17.1 원칙

  • GPT에 raw 테이블 전체를 직접 주지 않는다.
  • SQL/Rule/Mart가 사실과 계산을 먼저 확정하고 GPT는 해석·우선순위·대안 생성에 사용한다.
  • 출력은 고정 JSON Contract로 저장하고 자유 채팅을 메인 UX로 만들지 않는다.

17.2 Fact/Interpretation/Hypothesis 분리

  • Fact: DB·수집·계산으로 확인된 값.
  • Interpretation: Fact에 대한 의미.
  • Hypothesis: 아직 검증되지 않은 원인.
  • Evidence: High/Medium/Low.
  • Risk → Impact → Mitigation → Recommendation → Next Action 구조로 Case를 생성한다.

17.3 Source 부족

  • Source가 없으면 정상/0으로 채우지 않고 NOT_AVAILABLE/DATA_GAP.
  • 필수 기준이 미확정이면 임의 기준을 만들어 자동 실행하지 않고 운영자 결정 요청.

18. Content Factory와 신규 마케팅 생성

18.1 Keyword/SEO Factory

  • 신규 광고 키워드, SEO 성장 키워드, 상품명/해시태그 후보 생성.

18.2 SA Creative Factory

  • 고성과 검색어·구매 키워드·광고문안 특성 기반 SA 카피 후보 생성.

18.3 GFA Creative Factory

  • 성과 좋은 소재/타겟/지면 패턴 기반 이미지 브리프, 카피, CTA, 캠페인 세팅 가이드 생성.

18.4 SNS Package

  • VOC Needs + 키워드 수요 + 판매/순위 시그널로 블로그/인스타/페이스북/유튜브 스크립트 초안 패키지 생성.
  • 1차는 draft/reviewed/approved 수준이며 자동 게시보다 검수 가능한 초안 품질을 우선.

19. 실행·검증·학습

19.1 사람 승인형 실행

  • 돈·브랜드 위험 액션은 기본 수동 승인.
  • 1차 성공 기준은 자동 집행이 아니라 사람이 5분 이내 실행 가능한 구체 Work Order를 만드는 것.

19.2 Outcome

  • 작업별 검증 기간과 성공 조건을 반드시 저장.
  • D+3/7/14/30의 비용·매출·순위·CVR·ROAS·VOC 변화를 작업 전 Baseline과 비교.

19.3 Learning

  • 승인/반려와 실제 Outcome을 policy pack, prompt, threshold 추천 근거에 반영.
  • 같은 유형 Case에서 어떤 선택이 실제로 이겼는지 누적.

20. UI/UX 기술 규격 - 종합상황실

20.1 1분 인지 원칙

  • 긴 텍스트 카드 금지. 핵심 수치·상태·Top N·Action을 기본 노출.
  • 위험은 빨간 점멸(심각 이슈에 한정), 안정/상승 녹색, 주의 노랑, 집중 주황, 데이터 부족 회색.
  • 문제가 없는 영역은 축약. 문제/기회가 있는 경우에만 상세 영역 활성화.

20.2 레이아웃

  • 상단 Executive Summary.
  • 중앙: Risk / Optimize / Opportunity / Validate 4개 Queue.
  • 하단 또는 우측: 분야별 상태 Heatmap, 오늘의 실행, 데이터 신뢰도.
  • 각 카드 클릭 시 대응 Sub 상황실로 이동.

21. UI/UX 기술 규격 - Sub 상황실

21.1 공통 템플릿

  • Snapshot → Risk → Optimize → Opportunity → Evidence → Operator Decision → Work Order/Outcome.
  • 분야 특성에 따라 표/차트/매트릭스를 다르게 사용하되 상태/Action 의미는 통일.

21.2 상세 분석 연결

  • Sub 상황실은 원천 데이터 그리드가 아니라 '무엇을 해야 하는지'를 압축.
  • 근거를 클릭하면 현재 SA/GFA/키워드/순위/판매/리뷰/Q&A 분석 메뉴로 이동.

22. 데이터 신뢰도와 수집 건강도

22.1 필요성

  • 현재 수집 안정성은 작업별로 다르며 CDP 의존 경로의 실패/부분 성공이 실제로 존재한다.
  • 따라서 위험 신호가 사업 변화인지 데이터 누락인지 먼저 구분해야 한다.

22.2 구현

  • 각 판단에 data_freshness, coverage, last_success_at, source_status 포함.
  • 종합상황실에 데이터 신뢰도/수집 장애를 별도 표시.
  • 실패한 수집이 성공 데이터를 덮어쓰지 않는 기존 저장 정책 유지.

23. 구현 Roadmap

Block 0 - Contract Lock / Gap Audit

  • 현재 A-1~E-14, AI Ops, 상세 메뉴, DB/API를 종합상황실 요구사항에 매핑.
  • 공통 Status/Opportunity/Case Contract 확정.
  • 새 UI 전에 Source 없는 필드와 중복 로직 식별.

Block 1 - Decision Mart 강화

  • 트렌드/A-1 정식 편입.
  • SKU health, domain status, risk/optimize/opportunity 후보를 일자별 materialize.
  • 종합상황실이 raw fact를 직접 계산하지 않도록 중간 Mart 구성.

Block 2 - 종합상황실 v1

  • Executive Summary + 분야별 상태 + Risk/Optimize/Opportunity/Validate Queue.
  • Normal Mode에서는 A-1~E-14 상태만 축약.
  • Issue Mode에서 관련 Sub 상황실 Drill-down.

Block 3 - Keyword/Organic + SA Sub 상황실

  • 광고 키워드 + 오가닉 키워드 + 구매 키워드 통합.
  • CPC/순위 조절, 신규 광고/SEO 키워드 발굴.
  • SA 캠페인/그룹/키워드 최적화 Work Order.

Block 4 - GFA Sub 상황실 + Content Factory

  • 소재×타겟×성별×연령×지면 매트릭스.
  • 소재 피로/성과 패턴 분석.
  • Creative Brief 및 신규 소재 후보 생성.

Block 5 - SKU/Customer/VOC/Trend Sub 상황실

  • 상품·매출·상품지수·리뷰·Q&A·고객/전환·수요를 SKU-first로 연결.
  • 광고 확대 전 VOC gate, FAQ/상세페이지 작업지시.

Block 6 - Case/Work Order/Outcome Loop

  • 7개 Case 유형을 공통 Work Order/Outcome Contract로 통합.
  • D+3/7/14/30 검증 타임라인.

Block 7 - Learning + Controlled Publish

  • Outcome 기반 policy pack 갱신.
  • 저위험 게시부터 단계적 Publish Adapter.
  • SA 예산/입찰 자동화는 가장 마지막.

24. 완료 기준 / QA

24.1 종합상황실

  • 운영자가 1분 안에 전사 상태, 가장 중요한 위험, 개선 후보, 신규 기회, 검증 대기 작업을 구분한다.
  • 세부 분석 데이터를 읽지 않아도 어디로 Drill-down해야 하는지 안다.

24.2 Sub 상황실

  • 각 분야에서 현황/위험/개선/기회 4축이 명확하다.
  • 추천 Action의 근거 Source와 상세 분석 링크가 존재한다.
  • Source 없는 숫자/판정 생성 0.

24.3 실행/학습

  • 운영자 결정 → Work Order → 실행 완료 → Outcome이 동일 lineage로 연결된다.
  • 승인만 하고 끝나는 티켓이 아닌 검증 가능한 작업 단위가 된다.

24.4 비기능

  • 현재 수집/DB/배포 안정성 훼손 0.
  • 기존 상세 분석 메뉴 회귀 0.
  • 각 도메인 추가가 종합상황실 core에 대규모 조건문을 추가하지 않는 구조.

25. 주요 Risk와 대응

25.1 Scope Creep

  • Risk: 상황실을 만들며 기존 분석 기능을 중복 구현.
  • Impact: 유지보수 비용과 판단 불일치 증가.
  • Mitigation: 기존 메뉴는 Evidence, 신규 상황실은 Projection/Decision 전용.
  • Recommendation: 새 분석 알고리즘은 Sub 상황실 요구로 반드시 필요한 경우에만 별도 Block으로.

25.2 잘못된 자동화

  • Risk: AI 추천을 바로 광고비/입찰/브랜드 게시에 자동 적용.
  • Impact: 비용·브랜드 손실.
  • Mitigation: 승인형 실행, Work Order, 롤백/감사.
  • Recommendation: 자동 게시/입찰은 Outcome 근거가 충분한 저위험 영역부터 단계적.

25.3 데이터 누락을 사업 이상으로 오판

  • Risk: CDP 실패/미수집을 매출·순위 급락으로 해석.
  • Impact: 잘못된 조치.
  • Mitigation: freshness/coverage/source status를 판단 필수 입력으로.

25.4 추천 폭증

  • Risk: 데이터가 많아 하루 수백 건의 기회/개선 추천 생성.
  • Impact: 운영자 피로.
  • Mitigation: SKU-first, 영향도×근거×실행가능성으로 우선순위, '오늘 손댈 일' 제한.

26. 최종 Target Architecture

26.1 계층

  • Presentation: 종합상황실 + Sub 상황실 + 기존 상세 분석 메뉴.
  • Orchestration: Decision Engine + Opportunity Engine + Action Queue + Content Factory + Publish Adapter.
  • Decision Mart: product/domain health + decisions + cases + work orders + outcomes.
  • Generation Artifacts: keyword/copy/creative/SNS/FAQ/SEO assets.
  • Fact Layer: Ads/GFA/Rank/Sales/Purchase/Review/Q&A/SEO.
  • Config/Policy: AI settings, SKU policy pack, thresholds, category dictionaries.

26.2 확장성

  • 향후 현재 프로그램과 유사한 크기의 분석 영역이 2개 이상 추가되더라도 각 도메인이 공통 Domain Status/Case Contract를 출력하도록 한다.
  • 종합상황실은 신규 도메인의 status/queue만 소비하므로 핵심 구조를 재설계하지 않는다.

27. 결론

27.1 최종 판단

  • 현재 ERP2 Analytics는 Collect와 Analyze 자산이 이미 강하다.
  • 다음 핵심은 더 많은 상세 대시보드를 만드는 것이 아니라, 기존 Fact/분석을 종합상황실과 Sub 상황실이 소비하도록 구조화하고 Monitor→Optimize→Discover→Execute→Validate→Learn 루프를 닫는 것이다.
  • 종합상황실은 전사 관제와 성장 기회를 한눈에 보여주고, Sub 상황실은 분야별로 '현황·위험·개선·기회'를 운영자가 결정 가능한 Case로 바꾸며, 기존 상세 메뉴는 Evidence Source로 남긴다.
