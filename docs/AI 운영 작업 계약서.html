0. 지금 AI 운영센터가 실패한 이유 (코드 기준)

진단

화면은 점수·정책 라벨·「권장 액션」문장·「실행 큐로 보내기」버튼이다. 승인해도 네이버/콘텐츠에 아무 것도 안 바뀐다(수동 티켓 stub). 홈의 「즉시 검토」는 사실상 전체 SKU 수다. 운영자는 “그래서 내가 오늘 뭘 해야 하지?”를 화면에서 답을 못 얻는다.

이해먼저 상황을 한 장으로 읽게 한다
선택선택지는 최대 3개, 강제한다
지시서고르면 구체 작업지시가 남는다

1. 제품이 해야 할 일 (한 문장)

매일 아침, 운영자에게 “오늘 손댈 일 10건”을 주고 — 각 건마다 (1) 무슨 일이 생겼는지 숫자로 설명하고 (2) 왜 그게 문제/기회인지 말하고 (3) A/B/C 중 하나를 고르게 한 뒤 (4) 고른 순간 ‘누가·어디에·무엇을·얼마나’ 바꿀지 작업지시서를 만들고 (5) 며칠 뒤 효과가 났는지 같은 화면에서 보여준다.

인사이트 문장만 늘리는 기능은 만들지 않는다. “AI가 분석했습니다”는 제품이 아니다.

2. 화면 단위가 아니라 ‘사건(Case)’ 단위

메뉴 10개를 유지해도 된다. 다만 각 메뉴의 출력물은 KPI 카드가 아니라 아래 형식의 Case다. Case 없이 점수만 있으면 대시보드다.

Case 한 장의 필수 구성 (모든 도메인 공통)

구역 반드시 보여줄 것 금지
제목 대상 + 사건 (예: 「키워드 ‘무선이어폰’ — 7일 ROAS 38, 비용 42만」) AD_GROWTH, STOP·P1 같은 코드
상황 브리핑 3~5줄: 무엇이 변했는지 / 비교 기준(전주·목표) / 지금 왜 중요한지 점수만, 근거 없는 ‘위험’ 배지
근거 숫자 결정에 쓰는 지표만 3~6개. 클릭 시 기존 분석 메뉴로 원문 이동 다축 점수 나열(오가닉/광고/판매…를 카드에 다 붙이기)
강제 선택 버튼 2~3개. 고르기 전엔 ‘큐로 보내기’ 없음 「권장 액션: …」문장 + 단일 큐 버튼
작업지시 미리보기 선택지 hover/선택 시: 변경 대상·수치·담당·검증일 추상어: 집중 운영, 개선 우선, 테스트
결정 후 작업지시서 ID + 상태(대기/진행/검증중/종료) + D+7 결과 칸 승인만 하고 끝나는 티켓

3. 실제로 만들 사건 유형 7개 (이게 제품 범위)

이 7개만 완성하면 목표(판단·전략·Needs·광고 생성·SNS)의 핵심이 닫힌다. 나머지는 나중. 각 유형은 “보여주는 것 / 고르게 하는 것 / 남는 것”이 정의되어 있다.

Case A — 돈 새는 광고 (키워드/예산)

우선 1

목표: 오늘 줄이거나 늘릴 광고비를 숫자로 확정한다.

보여준다: 키워드·캠페인, 7일 비용/전환/ROAS, 전주 대비, (있으면) 오가닉 순위·잠식 여부, “이 비용이 순증인지” 한 줄.

고른다 (강제):

선택남는 작업지시
중단해당 키워드 OFF 또는 입찰 최저 · 담당: 광고 · 검증: D+3 비용=0/전환 변화
유지변경 없음 · 사유 메모 필수 · 재검토일 D+7
테스트입찰/예산 ±N% 또는 소재 1안 교체 · 기간 3일 · 성공조건 ROAS≥X

구현: 현재 광고 화면의 STOP/SCALE/TEST를 라벨 장식이 아니라 위 3버튼으로 교체. 큐 payload에 변경량·대상 ID·검증 조건을 필수로 넣는다.

Case B — 광고비 vs 실제 매출 (과투입)

우선 1

목표: “ROAS는 괜찮은데 돈을 너무 쓰는 SKU”를 잘라낸다.

보여준다: 순매출, 광고비, 광고비 비중, 환불률, “광고 없이 팔릴 가능성” 근거(오가닉 순위/구매키워드).

선택남는 작업지시
예산 축소SKU 광고비 −N% 또는 일예산 상한 · 검증: 순매출 유지 여부
현상 유지한도 메모 · D+7 재평가
매출 집중이 SKU로 예산 이동 후보 목록 생성(다른 Case A와 묶음)

Case C — 광고 전에 고쳐야 할 VOC

우선 2

목표: 광고 확대 금지/허용을 리뷰 이슈로 결정한다. Needs를 “주제”로 보여준다.

보여준다: 부정 비율·건수, 상위 불만 주제 3개(배송/사이즈/불량…), 최근 리뷰 원문 2~3개 인용, “지금 광고 확대 중인가요?”.

선택남는 작업지시
광고 확대 보류 + VOC 처리주제별 답글/개선 티켓 · 광고 확대 잠금 플래그
답글만리뷰 관리 초안 생성 큐로 연결(이미 있는 생성기 사용)
이슈 아님오탐 사유 · 학습 데이터로 저장

Case D — 구매 직전 막힘 (Q&A → FAQ)

우선 2

목표: 반복 문의 주제를 FAQ/상세 문장으로 고정한다.

보여준다: 같은 질문 N회, 구매 직전 비중, 대표 질문 원문, 현재 상세/FAQ에 답이 있는지 여부.

선택남는 작업지시
FAQ 등록질문·답변 초안 생성 → Q&A/콘텐츠 검수 → 게시 체크리스트
상세페이지 문구 수정수정 위치(스펙/배송/구성) + 문안 초안
개별 답변만기존 Q&A 초안 생성기로 연결

Case E — 순위 급락 / 방어

우선 3

목표: “광고를 더 할지, SEO/상품을 고칠지” 순서를 정한다. (기존 A-1 엔진 재사용)

보여준다: 핵심 키워드 순위 궤적, 원인 후보 1~2개(경쟁/상품지수/리뷰/재고), 지금 광고로 버티는지.

선택남는 작업지시
방어 광고 3일키워드·일예산·종료일 명시
상품/SEO 먼저상품명·태그·상세 작업지시 (SEO 메뉴 연결)
관찰알림 조건(N위 이탈)만 설정

Case F — 소재·카피 교체 (GFA/SA)

우선 4

목표: 분석 근거로 “이 소재를 끄고 / 이 초안을 올린다”를 결정한다.

보여준다: 저성과 소재 vs 고성과 패턴 요약, 생성기 초안 1~3개(이미 GFA 생성 있음), 예상 교체 효과는 사후검증으로만.

선택남는 작업지시
초안 A 채택검수 → usage_status=approved → (나중) 업로드 체크리스트
초안 재생성피드백 한 줄 필수 → 생성 재실행
기존 유지사유 저장

Case G — SNS/콘텐츠 패키지 (신규)

우선 5

목표: Needs+성과 스토리로 채널별 초안을 만들고 “쓸지/버릴지”만 고른다. 자동 게시는 이 단계에 넣지 않는다.

보여준다: 왜 이 상품/주제로 글을 쓰는지(판매·리뷰 강점·검색 수요 한 줄씩), 채널별 초안.

선택남는 작업지시
채택채널·본문·해시태그·이미지 프롬프트가 든 패키지 저장
수정 후 채택수정 지시 → 재생성
폐기폐기 사유 → 학습

4. 「오늘의 실행」이 실제로 보여야 하는 것

홈은 분석 허브가 아니다. Case A~E 중 오늘 선택 안 하면 돈이 새거나 기회가 죽는 것만 최대 10건.

홈 한 줄들어가서 하는 일끝
무선이어폰 — 비용 42만 / ROAS 38 — 중단 검토 Case A에서 중단/유지/테스트 선택 작업지시서 #… 생성
상품X — 광고비 비중 41% · 순매출 정체 — 과투입 Case B에서 축소/유지/집중 예산 상한 지시서
상품Y — 부정 리뷰 28% · 주제: 마감불량 — 광고 확대 중 Case C에서 보류+VOC / 답글 / 오탐 광고 잠금 + VOC 지시
상품Z — 같은 Q 14건 「구성품」 — FAQ 없음 Case D에서 FAQ/상세/개별답변 FAQ 초안 지시
홈에서 없앨 것

「즉시 검토 SKU = 전체 수」, 영어 버킷 칩, 「스냅샷 재생성」을 메인 CTA로 두는 것, 권장 문장만 있고 선택 버튼이 없는 카드.

5. 사람이 하는 일 vs 시스템이 하는 일

시스템

  • 수집된 fact로 Case 후보를 매일 만든다
  • 브리핑 문장 + 근거 숫자 + 원문 링크를 붙인다
  • 선택지별 작업지시 초안을 미리 채운다
  • 생성기(리뷰/Q&A/GFA/SNS)를 지시에 연결한다
  • D+3/D+7에 같은 Case에 결과 숫자를 채운다

사람 (슈퍼관리자/운영자)

  • 브리핑이 맞는지 30초~2분 확인 (틀리면 오탐 처리)
  • A/B/C 중 하나 고른다
  • 작업지시의 숫자(±N%, 문구)만 필요 시 수정
  • 실제 광고센터/스토어에 반영 (1차는 사람이 수행)
  • 「반영 완료」만 눌러 검증 타이머를 켠다
1차 성공 기준

네이버 API 자동 집행은 하지 않는다. 대신 “지시서가 얼마나 구체적이어서 사람이 5분 안에 실행 가능한가”가 성공 기준이다. 자동 집행은 지시서 품질이 검증된 뒤에만.

6. 결과적으로 화면에 남는 것 (이게 ‘학습’의 본체)

기록내용다음에 쓰임
Case상황 브리핑 스냅샷 + 근거 지표같은 유형 재발 시 비교
Decision사람이 고른 A/B/C + 수정한 수치정책/임계값 학습
Work Order실행 체크리스트 (대상 ID, 변경량, 담당)실제 반영·감사
OutcomeD+7 비용/매출/순위/VOC 변화선택지 승패 판정
Learning같은 유형에서 어떤 선택이 이겼는지다음 Case 우선순위·추천

지금 action_queue의 APPROVED는 Decision이 아니라 메모다. Work Order·Outcome이 없으면 학습도 없다.

7. 구현 순서 — 문서가 아니라 화면 교체

순서할 일완료의 정의 (데모로 증명)
1 Case 카드 UI 계약 고정 (브리핑·근거·3버튼·지시 미리보기) 광고 화면 1곳에서 중단/유지/테스트가 버튼으로 동작, 지시서 상세가 열림
2 Work Order 저장 모델 (선택·수치·검증일·상태) 승인 ≠ 완료. 「반영 완료」 후에만 검증 상태가 됨
3 홈을 Case 큐로 교체 (최대 10건, 돈/위험 순) 홈에서 바로 선택 가능. ‘전체 SKU 수’ KPI 삭제
4 Case B·C·D를 같은 카드 계약으로 이식 과투입/VOC/FAQ도 동일 UX
5 기존 생성기 연결 (리뷰·Q&A·GFA) 선택 ‘답글/FAQ/소재 채택’ 시 해당 메뉴 초안이 지시서에 붙음
6 Outcome 채우기 (스케줄) 지난주 중단한 키워드 Case에 D+7 결과 숫자가 보임
7 Case G SNS 초안 채택/폐기만 있는 패키지 화면

8. 지금 구조에서 버릴 것 / 살릴 것

버리거나 뒤로
  • 정책 타입 영어 배지 중심 UX
  • 「실행 큐로 보내기」단일 버튼
  • 승인만 하는 큐
  • 점수 6개를 카드에 다 붙이기
  • 트렌드 시나리오 문장만 있고 선택 없는 화면
  • 계획서용 FocusCard 장문
살릴 것
  • Fact 메뉴 전체를 근거 링크로 사용
  • 광고 STOP/SCALE/TEST·과투입·VOC/FAQ 후보 로직
  • 리뷰/Q&A/GFA 생성기
  • A-1 원인 분석
  • 수집 파이프라인
만들 것은 “AI 인사이트”가 아니라, 매일 Case를 읽고 A/B/C를 고르면 실행 가능한 작업지시가 쌓이고 일주일 뒤 결과가 같은 Case에 붙는 운영 책상이다.
